## 2. Storage Technology Evaluation

### Option A: PostgreSQL + TimescaleDB (Recommended)
**Pros**:
- Native time-series optimization with continuous aggregates
- Seamless PostgreSQL compatibility (already using Postgres)
- Automatic partitioning by time
- Built-in downsampling and retention policies
- JSONB support for flexible schema
- Excellent for real-time dashboards

**Cons**:
- Requires TimescaleDB extension installation
- Additional complexity in deployment

**Recommendation**: **Primary choice** for time-series analytics

### Option B: DuckDB for Analytics
**Pros**:
- Blazing fast OLAP queries (10-100x faster than Postgres for analytics)
- In-process database (no separate server)
- Perfect for complex aggregations and reports
- Excellent Parquet integration for data export

**Cons**:
- Not suitable for transactional workloads
- Would require ETL from PostgreSQL

**Recommendation**: **Secondary choice** for report generation and batch analytics

### Option C: Elasticsearch for Search
**Pros**:
- Full-text search across all entities
- Geospatial queries for clash location analysis
- Fast aggregations for dashboards
- Near real-time indexing

**Cons**:
- Additional infrastructure complexity
- Data duplication from PostgreSQL
- Resource intensive

**Recommendation**: **Stretch goal** for knowledge graph and semantic search

### Decision: Hybrid Approach

## 6. Predictive Modeling Approach

### 6.1 Time Series Forecasting Models

#### ARIMA (AutoRegressive Integrated Moving Average)
- **Use case**: Clash resolution rate prediction
- **Input**: Historical daily clash resolution rates (90 days)
- **Output**: 7-day forecast with confidence intervals
- **Library**: statsmodels (Python)

#### Prophet (Facebook)
- **Use case**: Project progress forecasting with seasonality
- **Input**: Daily progress percentages, holidays, project milestones
- **Output**: Completion date prediction with uncertainty bands
- **Library**: fbprophet (Python)

#### LSTM (Long Short-Term Memory)
- **Use case**: Multi-metric forecasting with dependencies
- **Input**: Multiple correlated metrics (clashes, progress, workflow velocity)
- **Output**: Multi-step ahead predictions
- **Library**: TensorFlow/Keras

### 6.2 Risk Prediction Models

#### Logistic Regression
- **Use case**: Project risk classification (low/medium/high)
- **Input**: Current KPIs, historical patterns, project attributes
- **Output**: Risk probability and contributing factors

#### Random Forest
- **Use case**: Clash severity prediction
- **Input**: Element types, disciplines, historical clash data
- **Output**: Predicted severity with feature importance

#### Gradient Boosting (XGBoost)
- **Use case**: Schedule delay prediction
- **Input**: Progress trends, workflow bottlenecks, resource allocation
- **Output**: Predicted delay in days with confidence

### 6.3 Model Training Pipeline

```python
# Pseudo-code for model training workflow

class PortfolioPredictiveModel:
    def train_forecast_model(metric_type, metric_name):
        # 1. Extract training data
        data = extract_metric_history(
            metric_type=metric_type,
            metric_name=metric_name,
            lookback_days=365,
            min_samples=90
        )

        # 2. Validate data quality
        if not validate_data_quality(data):
            raise InsufficientDataError()

        # 3. Feature engineering
        features = engineer_features(data)
        # - Lag features (t-1, t-7, t-30)
        # - Rolling statistics (mean, std over 7/30 days)
        # - Time features (day of week, month, quarter)
        # - External features (project size, type)

        # 4. Train/test split (80/20, time-based)
        train, test = time_series_split(features, test_size=0.2)

        # 5. Model selection and hyperparameter tuning
        models = [
            ARIMA_model(order=(p,d,q)),
            Prophet_model(seasonality_mode='multiplicative'),
            LSTM_model(units=50, dropout=0.2)
        ]

        best_model = cross_validate_models(models, train)

        # 6. Train final model
        final_model = best_model.fit(train)

        # 7. Evaluate on test set
        metrics = evaluate_model(final_model, test)
        # - RMSE, MAE, MAPE
        # - Confidence interval coverage
        # - Direction accuracy (up/down)

        # 8. Save model and metadata
        save_model(
            final_model,
            model_id=generate_model_id(),
            metrics=metrics,
            parameters=final_model.get_params()
        )

        return final_model
```

### 7.2 Data Segmentation

```sql
-- Row-level security policy for portfolio metrics
CREATE POLICY portfolio_metrics_access ON bim_fact_portfolio_metrics
  FOR SELECT
  USING (
    -- Admins see everything
    current_user_is_admin()
    OR
    -- PMO managers see all projects in their division
    project_key IN (
      SELECT project_key FROM bim_dim_projects
      WHERE division = current_user_division()
    )
    OR
    -- Project managers see their own projects
    project_key IN (
      SELECT project_key FROM bim_dim_projects p
      JOIN project_members pm ON p.project_id = pm.project_id
      WHERE pm.user_id = current_user_id()
        AND pm.role IN ('project_manager', 'bim_manager')
    )
  );
```

### 7.3 Data Anonymization for Benchmarking

```sql
-- Anonymized benchmark contribution
CREATE VIEW bim_anonymized_project_metrics AS
SELECT
  metric_type,
  metric_name,
  project_type,
  project_size,
  region,
  AVG(value) AS avg_value,
  STDDEV(value) AS std_dev,
  PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY value) AS median_value,
  COUNT(*) AS sample_size,
  NULL AS project_name,  -- Anonymized
  NULL AS project_id      -- Anonymized
FROM bim_fact_portfolio_metrics m
JOIN bim_dim_projects p ON m.project_key = p.project_key
WHERE p.contribute_to_benchmarks = true
GROUP BY metric_type, metric_name, project_type, project_size, region
HAVING COUNT(*) >= 5  -- Minimum sample size for anonymity;
```
